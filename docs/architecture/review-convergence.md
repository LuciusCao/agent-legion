# 评审收敛规则（codex / 自动评审 finding 分诊）

## 为什么需要

自动评审每轮都看完整 diff。如果每条 P2 都靠扩大改动范围来回应（新加抽象、新加防御分支），
新增的代码就会成为下一轮的靶子，评审永远不收敛。PR #835 是这种情况的典型：
需求本身只是给 `native-prod-up.sh` 加一行调用，最后做了 8 轮评审、14 条 finding、
+1700 行，其中至少 8 条 finding 打在前几轮修复新加的代码上。
防御边界不定义，就没有"修到哪算完"的标准。

## 轮次协议（#1150）

**单轮全量清单**：评审单轮输出完整问题清单（P0/P1/P2 分级排序），实现方一轮批量修复后
单轮复验。禁止每轮挤 1–2 条牙膏式回应（#797 十轮、#759 十二轮的历史就是这种模式）。

**同类二次分流**：同一类问题（焦点管理 / Dock 栈序 / 窄视口 / 时序竞态四个高频类）在静态
复审中第二次出现时，停止继续静态审——转 e2e/截图用例钉住行为，或升级为「实现策略是否
选错」的讨论。静态复审对这四类是弱工具（环境敏感、看不见运行时），别用它翻烧饼。

**第 5 轮熔断**：第 5 轮仍有新增 finding 时强制停下，写三行复盘（原方案是什么 / 最频繁的
问题类是什么 / 为何不收敛），然后从四个出口选一个，决策记入 PR 描述：

| 出口 | 适用信号 |
|---|---|
| 重估实现 | 同一区域反复出问题，补丁在跟框架/架构对抗（换路后轮次从 1 重新计） |
| 拆小 | PR 面积过大导致问题清不完（稳定部分先合，问题密集部分独立 PR） |
| 降级 issue | 剩余是打磨类（视觉细节/边界视口），不阻塞核心语义（进验收 backlog） |
| 转 e2e | 问题全是环境/时序敏感（写用例钉行为，静态审不再管这个类） |

**e2e 增量补齐**：上述四类问题转 e2e 时，顺手为该行为写 interaction 级用例（不追存量，
只补触碰到的）；新 e2e 用例必须遵守时序断言纪律（local-quality-gates.md 的
Timing-assertion discipline）——等信号非等时长、断言不变量、mock 真实形状，否则是把
flaky 搬进更慢的套件。

轮次计数无需新工具：commit subject 已带「codex 第N轮」标记，数分支提交即可。

## 分诊

**阻塞合并（当轮修）**

1. P1。
2. 在受支持的使用/部署形态下，会导致以下任一后果：PR 要修的缺陷仍然存在（含静默失效）、
   启动失败、数据丢失或损坏、安全边界被突破。
3. 本 PR 让既有路径出现回归。

**不阻塞（转 follow-up issue）**

- 只有在人为异常的文件系统或环境状态下才会触发的问题，例如 FIFO、目录形态的元数据文件、
  手写或伪造的指纹、相对 PATH 条目、恶意 symlink、损坏到非 UTF-8 的配置。
- 处理方式：在 finding 下回复判定理由并链接 issue，同类问题合并到同一个 issue。

"受支持的形态"以部署文档列出的为准（install-deps、native `make prod-up`、docker compose
等）。拿不准是否属于受支持形态时，判为阻塞，并在回复里写明理由。

## 回应方式

- 修阻塞项只能收窄或复用：优先删掉重复实现、复用已有 helper。
  需要新增抽象或新功能面才能修好的，说明 PR 范围本身过大，应拆成独立 PR。
- 一个 PR 只解决一个缺陷族；评审中发现的相邻问题另开 issue，不并进当前 PR。

## 停止条件

某一轮只剩不阻塞的 finding 时：完成分诊回复 → 确认 `quality-gate` 通过 → 合并，
**不再追加 `@codex review`**。
